# Contributing to Storyrr

Thanks for helping! Bug reports, translations and pull requests are all welcome.

Before writing code, read [AGENTS.md](AGENTS.md): it is the full reference for the stack, the architecture, the conventions and the integrations' pitfalls (humans and coding agents follow the same guide). The product spec is [docs/SPEC.md](docs/SPEC.md).

## Reporting bugs and ideas

- Search the existing issues first.
- For a bug, give the Storyrr version (Settings → About), what you did, what you expected and what happened, and the relevant lines from Settings → Jobs & logs.
- Remove hostnames, IP addresses, API keys, emails and library contents from anything you paste.
- For a bigger change or a new feature, open an issue to discuss it before the pull request.

**Security issues:** don't open a public issue. Report them privately through the repository's **Security** tab ("Report a vulnerability").

## Development setup

Requirements: [Node.js](https://nodejs.org/) 22.12+ (it runs the app) and [Bun](https://bun.sh/) (package manager and script runner only: never run the app with `bun --bun`, `better-sqlite3` doesn't work on Bun).

```bash
bun install
bun run dev   # http://localhost:6066, the first visit runs the setup wizard
```

No configuration is needed: the database goes to `database/dev.db` (git-ignored, like Laravel's `database/` folder), and the auth secret is generated next to it. To change something, copy `.env.example` to `.env.local` and uncomment the variable.

`.env.local` and the `*.db` files are git-ignored: never commit them.

| Script                | What it does                                                          |
| --------------------- | --------------------------------------------------------------------- |
| `bun run dev`         | Dev server with hot reload                                            |
| `bun run check`       | Message compile, format check, type-aware lint and tests (CI runs it) |
| `bun run format`      | Format with oxfmt (never align code by hand)                          |
| `bun run test`        | Vitest; use this, not `bun test`                                      |
| `bun run db:generate` | Generate a migration after changing `src/server/db/schema/`           |

## Making a change

- **Server code lives in `src/server/`** and takes its dependencies as arguments, so it can be tested against an in-memory database. Files in `src/functions/` only wrap it in server functions: every one that touches private data checks the session itself (`requireUser` / `requirePermission`).
- **Validation is Valibot** (never zod), for server function inputs, forms and external API responses.
- **UI** is composed from the shadcn components (React Aria base) in `src/components/ui/`; add new ones with the shadcn CLI rather than writing primitives by hand.
- **No hard-coded user-facing text:** every string is a Paraglide message. A new key goes into `messages/en.json`, `fr.json`, `de.json` **and** `es.json` in the same commit (see AGENTS.md › Conventions for each language's typography).
- **Database changes** come with their drizzle-kit migration (`bun run db:generate`), committed with the code.
- **Tests** sit next to the code as `*.test.ts`. New logic comes with tests; integrations are tested against fakes and recorded, sanitized fixtures.
- **Integrations:** read AGENTS.md › Integrations before touching Chaptarr, Audiobookshelf, Kavita, Komga, Jellyfin, Audible or Hardcover. Anything assumed but not checked against a real server or the service's source gets an `// UNVERIFIED:` comment.

## Translations

Translations live in `messages/<locale>.json`, with English (`en.json`) as the source. To fix a translation, edit the matching file. To add a language, add its file with every key and the locale to `project.inlang/settings.json`, then check that `bun run check` passes.

## Commits and pull requests

- Commits follow [Conventional Commits](https://www.conventionalcommits.org/), in English: `<type>(<optional scope>): <description>`, imperative and lowercase, e.g. `fix(chaptarr): send the media write scope on author updates`. Types, scopes and breaking changes are listed in AGENTS.md › Commits.
- Commit messages become the release notes: write them for users.
- One logical change per commit; `bun run check` passes on every commit.
- Keep pull requests focused, and describe what changes for users and how you tested it (screenshots for UI changes). If pull requests are squash-merged, the title follows the same format.
- Versions and `CHANGELOG.md` are generated by release-please: don't bump them by hand.

The repository is public: no personal data, hostnames, IP addresses or secrets in code, fixtures, commits or screenshots.
